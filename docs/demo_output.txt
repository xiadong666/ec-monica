  第 4 部分  意图路由：规则优先，出口有单向硬约束
══════════════════════════════════════════════════════════════════════════════

▸ 路由表
    analysis_report      需要工具       schema, metric, drilldown, quality, sql
    attribution          需要工具       schema, metric, drilldown, quality, sql
    requirement_parse    需要工具       schema, sql
    direct_generate      直接生成       （不装配）

▸ 实际路由（含硬约束把关）
    上周的 GMV 是多少          → analysis_report                    用工具  (rule)
    转化率为什么下滑了            → attribution                        用工具  (rule)
    分析一下这个需求文档           → requirement_parse                  用工具  (rule)
    写个 618 促销文案          → direct_generate                    直接生成  (rule)

▸ 单向硬约束（enforce_data_signal）
    规则：含数据信号的请求，绝不允许判为「直接生成」

    为什么是单向的？两个方向的代价不对称：
      · 误判为免工具 → 模型凭记忆编数字，输出格式仍完全正确，用户看不出问题
      · 误判为需工具 → 只是多查一次数据，成本可接受
  └─ 所以宁可多查，不可编造。

  第 5 部分  工具层：注册、容错、错误分类与自我修正
══════════════════════════════════════════════════════════════════════════════

▸ 已注册工具（13 个，按能力标签装配）
    drilldown    6            get_product_breakdown, get_channel_breakdown, scan_stockout, scan_price_change, get_cross_breakdown, get_competitor_price
    metric       3            compare_weeks, get_period_summary, get_ad_trend
    quality      3            scan_stockout, scan_price_change, run_quality_checks
    schema       2            describe_tables, get_data_range
    sql          1            run_sql

▸ 安全护栏：写操作必须被拒
  ✓ 已拒绝：SQL 被拒绝：只允许 SELECT / WITH 查询

▸ 错误分类：确定性错误不重试，直接告诉模型怎么改
    错误信息                : 列名不存在：p.product_name
    错误类型                : data  →  不重试（重试同样失败）
    修正建议                : ['title']
    提示原话                : 数据库中不存在列「p.product_name」。最接近的真实列名是：title。注意：商品名是 dim_product.tit
  └─ 把裸报错翻译成「正确的列名是什么」，模型下一轮就能改对。

▸ 参数别名自动纠正（模型常把 start 写成 start_date）
  ✓ 错误参数名被拒：参数名错误：scan_stockout 不接受参数「foo」。正确参数为 ['end', 'start']。
       结构化字段 expected_params = ['end', 'start']
  ✓ start_date → start 已自动映射：返回 1 条，P001 缺货 7 天
  └─ 别名表只收录语义明确等价的写法；可疑的组合名一律拒绝。
  └─ 原因：静默算错比直接报错危险 —— 报错会让模型改，算错会进最终报告。

▸ 自适应并发决策（并行不一定更快）
    快工具（本地 SQLite，毫秒级）→ 串行
      预估加速比 0.23x < 1.15x：工具总耗时约 6ms、最慢 3ms，不敌线程池开销约 25ms，串行更快
  └─ 并行墙钟 ≈ max(单个) + 线程池开销；串行 ≈ sum(单个)。
  └─ 本地工具 12~20ms，线程池开销 20~30ms —— 并行会变成负优化。

    评测层（pytest，离线）：6 个能力层共计 44 项断言

  └─ 离线层的准确率本身就是指标：它衡量「确定性骨架」的健康度。
